# Model-Role Research Method

Use this reference for a documentation or research-only role recommendation.
It does not authorize gateway mutation, paid probing, provider access, backup,
or promotion.

## Evidence and date

For every material claim, record source URL, publisher, publication/access date,
model version, effort, route, harness, and task class. State whether the source
is primary documentation, an independent evaluation, or local proof.

Do not read credentials, environment variables, provider records, account
catalogs, or live endpoints merely to research a model. A dated source can
support a hypothesis, not current availability, authorization, price, effective
route, tool capability, or runtime health.

## Refresh sequence

1. Freeze the question, target role, and date/access boundary.
2. Prefer the model owner's current documentation for identity, availability,
   version and documented route; retain its publication/update date.
3. Add current independent benchmark owners only when their harness and task
   class bear on the question. Record benchmark run date separately from source
   publication and access dates.
4. Deduplicate evidence by originating publisher or benchmark owner; mirrors,
   news summaries, and copied leaderboards are not independent votes.
5. Compare exact version, effort, route, harness, task class and metric before
   using a result. Different benchmark indexes/versions are separate rows, not
   values to aggregate.
6. Seek contradictions deliberately. A stale, unreachable, version-mismatched,
   or non-entailing source is retained with its disposition, then abstained from;
   it is not silently converted into support.

## Adversarial votes

Keep documentation and independent evaluation as separate votes:

- `direct`: supports the exact model, version, effort, route, and claim;
- `partial`: useful but differs in one or more of those dimensions;
- `abstain`: insufficient evidence.

The operational recommendation is a labelled inference, not a fabricated third
measurement or internet consensus. Marketing positioning is not local quality
proof. Do not generalize a result at `max` to `medium`, a tool harness to a
no-tools Web route, or one provider/account to another.
Keep a proposed recommendation distinct from an applied local policy; only the
authorized policy owner may adopt it after the required qualification.

## Evidence table

Use one row per source with: claim; source URL and origin; source type; model
and version; effort; route; harness/task denominator; metric; publication,
benchmark-run, and access dates; vote; limitations; and contradiction/staleness
disposition. Keep the final recommendation in a separate field labelled
`inference`. Never use empty provider/configuration discovery as a research
fallback.

## Output

Return the question, evidence table, constraints, dated hypothesis, and exact
next local qualification needed. Say `unknown` where the denominator is absent.
Do not edit an alias or role policy from research alone.
