Codex global skill catalog, specialist agents, and quality stack

Objective and current truth

Reduce the default Codex prompt to a compact orchestration core without deleting capabilities, route specialized work through explicit logical profiles, make SDD and TDD first-class pre-code contracts, and keep Plane issue execution complete, governed, and read-backed.

The effective catalog authority is adapters/runtime/codex/skill-catalog-manifest.toml. The current denominator is 131 skills. Exactly 13 are visible in the default root: eight repo-governed orchestration skills plus five Codex system skills. The remaining capabilities are specialist or on-demand and are not deleted.

Problem and measured evidence

The original runtime exposed a broad set of specialist skills to the default root and emitted the warning that skill descriptions were shortened to fit the context budget. The first pre-restart correction reduced the catalog but still left 39 skills effective because 20 repo skills and 14 host Superpowers skills remained resident alongside five system skills. A real post-restart startup reproduced the warning, proving that static compactness alone was not a sufficient oracle.

The Plane work item also originally lacked sufficient body detail and lifecycle discipline. Its body must remain execution-ready and current rather than relying on a title or stale historical counts.

Profiles are additive process configurations selected with codex -p <name>. They are not credential, filesystem, tool, MCP or physical-agent isolation. Native collaboration spawn receives a bounded assignment, model and reasoning effort; it does not prove injection of a logical profile.

Specification and quality lifecycle

  • Every mutation enters a proportional Specification Lifecycle: micro, standard, hierarchical or critical.
  • SDD, ADR, DESIGN, Test Design, threat, rollout, rollback, observability and AGENTS dispositions are explicit before implementation.
  • Traceability is requirement to task to stable case to observed proof.
  • TDD selects Red/Green/Refactor, failing repro, characterization, semantic contract, migration, security, UI or provider proof according to the change.
  • Code review covers correctness, legibility, architecture, security, performance, tests and proof without collapsing specialist authority.
  • Security review starts at trust boundaries and includes STRIDE, abuse variants, supply chain, exploitability, safe-PoC disposition and negative proof.
  • Test engineering preserves independent acceptance; web performance distinguishes static opportunity from measured evidence; minimalism cannot remove safety or proof.
  • Nine quality/workflow skill packages use progressive disclosure, reviewed package snapshots and fail-closed eval-fixture validation without claiming unperformed LLM replay.

Plane and hook governance

  • Plane is the sole issue authority and is accessed only through the governed MCP.
  • Issue creation requires substantive objective, context, scope, non-goals, acceptance, owner, priority, dependencies, validation and execution units; descriptors expose the exact payload fingerprint field.
  • Lifecycle comments use START, PROGRESS, BLOCKED, REVIEW and FINISH with mutation receipt and provider readback.
  • The passive Orca hook path is removed from the active contract by an explicit empty hooks configuration. This is removal of a misleading passive hook, not a claim that hooks enforce governance.

Acceptance criteria

  1. The catalog validates at inventory=131 enabled=13 with no duplicate identifier/path, wildcard or uncovered disabled capability.
  2. The default root effective inventory is exactly 13; Python 25; Next.js 30; research 19; reviewer 26; QA 18.
  3. Each of the six contexts completes an ephemeral read-only startup turn with an exact readiness token and zero skill-description-shortening errors.
  4. Superpowers remains recoverable through superpowers-on-demand; system skills remain unmanaged by the catalog reconciler.
  5. Unknown or stale profiles fail closed; the root is bare codex, never -p orchestrator.
  6. Repo source precedes global deployment. Sync is atomic, preserves unrelated config/MCPs/packages, records a schema-3 receipt, and has tested rollback.
  7. Focused lifecycle, agent, skill, catalog, topology, install, stage and runtime gates pass; the full repository suite passes.
  8. A bounded no-history spawn returns evidence, findings, self-review and self-forensic review while root retains integration and closure.
  9. Plane lifecycle writes have semantic preflight, narrow authorization, idempotency, mutation receipt and independent provider readback.
  10. No capability, plugin, MCP, credential, cache or user-owned configuration is silently deleted.
